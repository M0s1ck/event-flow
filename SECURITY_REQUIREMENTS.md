# Требования безопасности

| ID | Требование | Критерий приёмки | Связанные T |
| --- | --- | --- | --- |
| SR-01 | Регистрация на мероприятие, отмена регистрации, публикация мероприятия, просмотр своих регистраций и списка участников доступны только вошедшему пользователю. Без входа доступен только список мероприятий и число свободных мест. | Запрос на регистрацию без входа отклоняется: запись не создаётся, число свободных мест не меняется. Запрос списка мероприятий без входа выполняется успешно. | T-06 |
| SR-02 | Вход выполняется только при правильной паре логин/пароль, а пароль пользователя не раскрывается: не возвращается в ответах API и не хранится в базе в открытом виде. | При неверном пароле вход отклоняется и сессия не выдаётся; при верном — выдаётся. Ни один ответ API (профиль, список участников и т.д.) не содержит пароль или его хэш; в таблице пользователей значение поля пароля не совпадает с введённым паролем. | T-08, T-10 |
| SR-03 | Запись на мероприятие создаётся только от имени того пользователя, который вошёл в систему. Участник не может записать на мероприятие другого человека, даже если укажет в запросе его идентификатор. | Пользователь A отправляет запрос регистрации с идентификатором пользователя B в теле запроса → у B не появляется новой регистрации (запрос отклоняется или запись создаётся на A). Обычная регистрация A на мероприятие проходит успешно. | T-06 |
| SR-04 | Участник может отменить только свою регистрацию. Знание идентификатора чужой регистрации не даёт права её отменить. | Пользователь B отправляет запрос отмены регистрации пользователя A по её ID → запрос отклоняется, регистрация A остаётся активной, число свободных мест не меняется. Сам A может отменить свою регистрацию, после чего число свободных мест увеличивается на 1. | T-01 |
| SR-05 | Число активных регистраций на мероприятие никогда не превышает его вместимость, в том числе при одновременных запросах. Отказ в регистрации не меняет состояние мероприятия. | На мероприятие с 1 свободным местом два разных участника одновременно отправляют запрос регистрации → успешно проходит ровно один, второй получает отказ; в базе одна активная регистрация, свободных мест 0 (а не −1). На заполненное мероприятие регистрация отклоняется, новых записей не появляется. Повторная отмена уже отменённой регистрации не увеличивает число свободных мест. Ссылка: `v5.0.0-2.3.4`. | T-02, T-03, T-04 |
| SR-06 | Один пользователь может иметь не больше одной активной регистрации на одно мероприятие (иначе один человек может занять все места). | Участник, уже записанный на мероприятие, повторно отправляет запрос регистрации (в том числе несколько раз подряд) → повторные запросы отклоняются, у участника остаётся одна активная запись, число свободных мест уменьшилось только на 1. | T-04 |
| SR-07 | Публиковать мероприятия может только пользователь с ролью «Организатор». Участник не получает это право даже при прямом обращении к API. | Участник отправляет запрос публикации мероприятия напрямую в API → запрос отклоняется, новое мероприятие не появляется в общем списке. Организатор с теми же данными мероприятия успешно его публикует. | T-07 |
| SR-08 | Роль пользователя задаётся при создании аккаунта, и пользователь не может сам изменить её через API. | Участник отправляет запрос на изменение своего профиля с полем роли «организатор» → роль остаётся «участник», последующая попытка опубликовать мероприятие отклоняется. | T-09 |
| SR-09 | Список участников мероприятия (имена, контакты) виден только организатору этого мероприятия. | Организатор мероприятия X получает список участников X. Другой организатор или участник (в том числе записанный на X) запрашивает список участников X → запрос отклоняется, имена и контакты участников в ответе не возвращаются. | T-05 |
| SR-10 | Пароль пользователя нельзя подобрать перебором: система ограничивает число неудачных попыток входа в один аккаунт. | После 5 неверных паролей подряд для одного логина следующие попытки входа в течение некоторого времени (например, 15 минут) отклоняются, сессия не выдаётся. После окончания этого времени пользователь входит с верным паролем. | T-08 |
| SR-11 | В ответах API, доступных без входа или другим пользователям, нет контактов и служебных данных людей: публичный список мероприятий показывает только данные мероприятия и имя организатора. | Гость запрашивает список мероприятий и одно мероприятие → в ответе есть название, описание, дата, вместимость, свободные места и имя организатора, но нет его email/телефона, логина, пароля или хэша и внутренних полей записи «Человек». | T-10 |

Допущения:
- роль (организатор или участник) выбирается один раз при создании аккаунта;
- без входа можно только смотреть список мероприятий и число свободных мест.
