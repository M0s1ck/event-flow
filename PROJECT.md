# Паспорт проекта

## Общие сведения

**Название команды:** dev sell ops
**Название продукта:** event flow
**Коды участников:** `M1`, `M2`, `M3`
**Статус ранней калибровки:** `черновик`

*После обратной связи преподавателя обновите статус: `согласовано`, `согласовано с условиями`, `требуется корректировка` или `требуется другая тема`.*

## 1. Назначение

Event Flow — сервис регистрации на мероприятия. Организатор публикует мероприятие с указанием вместимости (числа мест), а участники просматривают список мероприятий, регистрируются на понравившееся и при необходимости отменяют участие. Продукт решает проблему учёта записи и контроля свободных мест: система не позволяет зарегистрироваться сверх вместимости и сразу освобождает место при отмене. Результат получают и участники (актуальный список своих регистраций и доступных мест), и организаторы (достоверный список записавшихся на своё мероприятие).

## 2. Граница продукта

**В продукт входит:**

- публикация мероприятия организатором с указанием названия, описания, даты/времени и вместимости;
- просмотр списка мероприятий и количества свободных мест;
- регистрация участника на мероприятие с учётом оставшейся вместимости;
- просмотр участником списка собственных регистраций;
- отмена участником собственной регистрации с освобождением места;
- просмотр организатором списка участников своего мероприятия.

**Внешнее окружение и внешние системы:**

- способ входа в систему — логин и пароль, аккаунт создаётся в самом сервисе; после входа сервер выдаёт токен сессии, по которому определяет пользователя (внешние системы входа не используются);
- хранилище данных (база данных), к которому обращается сервер.

**Команда сознательно не реализует:**

- уведомления по email или push;
- оплату участия и штрафы за неявку;
- мобильное приложение;
- интеграцию с внешними календарями;
- полноценный пользовательский интерфейс — достаточно веб-API и минимального клиента.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Организатор | Пользователь, публикующий мероприятия | Публиковать мероприятие с указанием вместимости; просматривать список участников своего мероприятия; отменять мероприятие; отменять регистрацию отдельного участника своего мероприятия | Регистрироваться на мероприятия как участник в рамках своего же мероприятия; просматривать или изменять участников чужих мероприятий |
| Участник | Пользователь, желающий посетить мероприятие | Просматривать список опубликованных мероприятий и число свободных мест; регистрироваться на мероприятие при наличии свободных мест; просматривать список своих регистраций; отменять собственную регистрацию | Публиковать мероприятия; изменять вместимость мероприятия; просматривать или отменять регистрации других участников |

Просмотр списка опубликованных мероприятий и количества свободных мест доступен без входа в систему; регистрация и отмена регистрации требуют входа. Роль (организатор или участник) — атрибут сущности «Человек», см. раздел 5. Роль выбирается пользователем один раз при создании аккаунта и дальше через API не меняется. Права организатора распространяются только на его собственные мероприятия.

## 4. Сквозные сценарии

### Сценарий 1. Регистрация на мероприятие

- **Участники:** Участник
- **Начальное условие:** Мероприятие опубликовано организатором, есть хотя бы одно свободное место
- **Основные действия:** участник просматривает список мероприятий → открывает мероприятие и видит число свободных мест → регистрируется на него
- **Результат:** участник добавлен в список зарегистрированных на мероприятие и видит эту регистрацию у себя
- **Какие данные или состояние изменяются:** создаётся запись регистрации; уменьшается число свободных мест мероприятия

### Сценарий 2. Отмена регистрации

- **Участники:** Участник
- **Начальное условие:** у участника есть активная регистрация на мероприятие
- **Основные действия:** участник открывает список своих регистраций → выбирает нужную → отменяет её
- **Результат:** место снова становится доступным для регистрации других участников
- **Какие данные или состояние изменяются:** статус регистрации меняется на «отменена»; увеличивается число свободных мест мероприятия

### Сценарий 3. Публикация мероприятия

- **Участники:** Организатор
- **Начальное условие:** у организатора есть данные о мероприятии (название, дата, вместимость)
- **Основные действия:** организатор заполняет название, описание, дату/время и вместимость мероприятия → публикует его
- **Результат:** мероприятие становится видимым в общем списке и доступным для регистрации участников
- **Какие данные или состояние изменяются:** создаётся новая запись мероприятия со статусом «опубликовано» и числом свободных мест, равным вместимости

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Человек (имя, контакты, роль — организатор/участник) | Сам пользователь, остальные пользователи, система (для проверки прав) | Раскрытие имени и контактов третьим лицам нарушает приватность пользователя | Неправомерное изменение роли даёт чужому человеку права организатора или отбирает их; удаление или недоступность записи лишает человека доступа к своим мероприятиям и регистрациям, а связанные мероприятия/регистрации теряют владельца |
| Мероприятие (название, описание, дата, вместимость, статус) | Организатор, участники | Как правило, публичная информация; не критично | Неправильное изменение вместимости приводит к переполненности мероприятия или к необоснованному отказу в регистрации; удаление мероприятия лишает всех зарегистрированных участников информации об участии; недоступность мешает и просмотру, и публикации мероприятий |
| Запись человека на мероприятие (регистрация: кто, на какое мероприятие, статус) | Участник (владелец регистрации), организатор мероприятия | Раскрытие списка участников третьим лицам нарушает приватность (кто на какое мероприятие записан) | Неправомерная отмена чужой регистрации лишает участника места без его согласия; создание регистрации в обход проверки вместимости приводит к переполненности мероприятия; недоступность регистраций не даёт участникам записаться или отменить участие |

## 6. Компоненты и внешние взаимодействия

- **Сервер (веб-API):** реализует предметную логику — публикацию мероприятий, регистрацию и отмену регистрации с проверкой вместимости, выдачу списков мероприятий и участников.
- **Хранилище данных:** база данных, в которой сохраняются три сущности — Человек, Мероприятие и Запись (регистрация человека на мероприятие); сервер читает и изменяет данные при каждом сценарии.
- **Клиент:** минимальный веб-клиент или обращения напрямую к API (через Swagger/Postman на раннем этапе) для организатора и участника.

Актуальная схема компонентов, точки входа API и границы доверия — в разделе «Модель продукта» [THREAT_MODEL.md](THREAT_MODEL.md).

Взаимодействие: клиент отправляет запросы к серверу (создать мероприятие, получить список мероприятий, зарегистрироваться, отменить регистрацию, получить список участников); сервер проверяет права и состояние (например, наличие свободных мест) и читает/изменяет данные в хранилище, возвращая клиенту результат.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Форма/запрос публикации мероприятия | Название, описание, дата, вместимость | Организатор | Создаёт запись мероприятия и инициализирует число свободных мест |
| Форма создания аккаунта и входа | Логин, пароль, имя, контакты, роль | Пользователь | Создаёт запись «Человек», при входе проверяет пароль и выдаёт токен сессии |
| Запрос регистрации | Идентификатор мероприятия (участник определяется сервером по токену сессии, а не по полю запроса) | Участник | Создаёт запись регистрации, если есть свободные места, и уменьшает их число |
| Запрос отмены регистрации | Идентификатор регистрации | Участник (владелец регистрации) | Помечает регистрацию отменённой и увеличивает число свободных мест мероприятия |

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- публикация мероприятия организатором с указанием вместимости;
- просмотр списка мероприятий и числа свободных мест;
- регистрация участника на мероприятие с учётом вместимости (нельзя зарегистрироваться, если мест нет);
- просмотр участником списка своих регистраций;
- отмена участником собственной регистрации с освобождением места;
- просмотр организатором списка зарегистрированных участников своего мероприятия.

**Функции, которые можно исключить при нехватке времени:**

- список ожидания при заполненном мероприятии;
- модерация публикаций мероприятий;
- отмена организатором регистрации отдельного участника;
- отмена организатором всего мероприятия;
- редактирование уже опубликованного мероприятия.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Go 1.26 (веб-API на роутере `github.com/go-chi/chi/v5`), PostgreSQL 16, драйвер `github.com/lib/pq` через `database/sql`, SQL-миграции встроены в бинарник и применяются при старте (`internal/storage`), настройки из переменных окружения (`internal/config`), Docker Compose для локального запуска.
**Технологии, новые для команды:** уточняется командой после первого технического опыта.
**Внешние сервисы, необходимые для запуска:** локальный экземпляр PostgreSQL (например, поднятый через Docker); внешних облачных сервисов не требуется.
**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** все три сценария (публикация мероприятия, регистрация, отмена регистрации) работают только с локальной PostgreSQL и не обращаются к внешним сервисам, поэтому для проверки достаточно локально поднятой базы данных.

**Что команда реализует первым, чтобы получить запускаемую версию:** минимальный Go-сервис со схемой БД (Человек, Мероприятие, Запись), эндпоинтами публикации мероприятия и регистрации на него, хранением данных в PostgreSQL.

## 10. Локальный запуск

**Требования к окружению:** Docker Desktop (или Docker Engine) с Docker Compose v2. Для запуска без Docker: Go 1.26+ и PostgreSQL 16.

**Команды установки и запуска** (из корня репозитория):

```bash
docker compose up --build
```

Поднимаются два контейнера: `db` (PostgreSQL) и `app` (сервер на `127.0.0.1:8080`). При старте сервер сам применяет миграции схемы.

Без Docker для сервера (БД всё равно нужна, например `docker compose up -d db`):

```bash
go run ./cmd/server
# основные переменные: DATABASE_URL (по умолчанию postgres://eventflow:eventflow@localhost:5432/eventflow?sslmode=disable), HTTP_ADDR (по умолчанию :8080)
# полный список и значения по умолчанию — internal/config/config.go
```

**Команда или запрос для проверки:**

```bash
curl http://127.0.0.1:8080/health
```

**Ожидаемый результат:** HTTP 200 и тело `{"db":"ok","status":"ok"}`. В логе `app` — строки `applied migration 001_init.sql` (при первом запуске) и `event-flow listening on :8080`.

Минимальный сценарий (по желанию):

```bash
curl -X POST http://127.0.0.1:8080/auth/register -H "Content-Type: application/json" -d '{"login":"org","password":"password123","name":"Org","contacts":"org@mail.ru","role":"organizer"}'
curl -X POST http://127.0.0.1:8080/auth/login -H "Content-Type: application/json" -d '{"login":"org","password":"password123"}'
# в ответе {"token":"..."}; дальше заголовок Authorization: Bearer <token>
curl http://127.0.0.1:8080/events
```

Остановить: `docker compose down` (с удалением данных БД: `docker compose down -v`).

*Это подтверждение запуска, а не доказательство выполнения всех требований безопасности.*
