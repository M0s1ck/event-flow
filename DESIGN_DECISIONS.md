### D-01. Пользователь определяется только по серверной сессии

**Контекст:** T-06 — если сервер берёт пользователя из поля запроса (`personId` в теле) или токен можно угадать/подделать, то любой может действовать от чужого имени, и все остальные проверки прав (D-02, роль организатора) теряют смысл. T-08 — пароль можно подбирать перебором. Связанные SR-01, SR-03 (действия только от своего имени), SR-02 (пароль не раскрывается), SR-10 (ограничение попыток).

**Решение:**

- После успешного входа сервер генерирует случайный токен 32 байта (`crypto/rand`) и отдаёт его клиенту. В таблице `sessions` хранится только SHA-256 от токена, `person_id` и `expires_at` (24 часа). `POST /auth/logout` удаляет строку сессии.
- Middleware `requireUser` берёт токен из заголовка `Authorization: Bearer ...`, находит неистёкшую сессию и по ней загружает из БД `id` и **роль** пользователя. Дальше обработчики берут пользователя только из контекста запроса.
- Ни один обработчик не читает идентификатор пользователя из тела, URL или других заголовков. `POST /events/{id}/registrations` вообще не читает тело; организатором нового мероприятия всегда становится текущий пользователь.
- Пароль хранится как PBKDF2-HMAC-SHA256 (600 000 итераций, случайная соль 16 байт), сравнение за постоянное время. После 5 неверных паролей подряд вход в аккаунт блокируется на 15 минут (SR-10). Для несуществующего логина сервер тоже считает хэш, чтобы по времени ответа нельзя было понять, есть ли такой логин.

Код: `internal/api/server.go` (`requireUser`), `internal/api/auth_handlers.go`, `internal/auth/auth.go`, таблица `sessions` в `internal/storage/migrations/001_init.sql`.

**Обоснование и сравнение вариантов.** Рассматривали два способа:

| | А. Сессия в БД (выбрали) | Б. Подписанный токен (JWT) с `id` и ролью внутри |
| --- | --- | --- |
| Как сервер узнаёт пользователя | ищет хэш токена в `sessions`, роль читает из `persons` | проверяет подпись, берёт `id` и роль из самого токена, в БД не ходит |
| Выход / блокировка | удалили строку — токен сразу перестаёт работать | токен работает до истечения срока; чтобы отозвать, нужен «чёрный список» в БД, т.е. та же таблица |
| Устаревшие данные | роль всегда актуальная | роль в токене может устареть |
| Что надо хранить в секрете | ничего, кроме БД; утечка дампа `sessions` не даёт рабочих токенов (там хэши) | ключ подписи; его утечка = можно выписать токен любому пользователю |
| Цена | +1 запрос к БД на каждый запрос с входом | без запроса к БД |

Главный компромисс — **отзыв токена против лишнего запроса к БД**. Для T-06 вариант (б) из модели («токен работает после выхода») прямо закрывается только вариантом А. Лишний запрос нам не мешает: у нас один сервер и одна БД, и каждая операция всё равно идёт в БД.

**Допущения и границы применимости:** один экземпляр сервера с одной БД; в реальном развёртывании перед сервером стоит HTTPS (сам сервер слушает HTTP, локально это допустимо).

**Когда пересмотреть:** если появятся несколько сервисов, которым надо проверять пользователя без доступа к общей БД, или нагрузка, при которой поиск сессии станет узким местом. Тогда — короткоживущий подписанный токен (минуты) + длинный refresh-токен в БД, который можно отозвать.

**Связанные угрозы:** T-06, T-08

**Связанные требования:** SR-01, SR-02, SR-03, SR-10

**Будущая проверка** (дополняет критерии SR-01, SR-03, SR-10):

1. **Условие:** пользователи A и B вошли, есть мероприятие со свободными местами. **Действие:** A отправляет `POST /events/{id}/registrations` с телом `{"personId": <id B>}`. **Ожидаемый результат:** запись создаётся на A; у B в `GET /registrations/my` и в таблице `registrations` записей нет.
2. **Условие:** A вошёл и получил токен. **Действие:** A делает `POST /auth/logout`, затем тем же токеном `GET /registrations/my`; отдельно — запрос с токеном, в котором изменён один символ, и запрос без заголовка. **Ожидаемый результат:** все три — 401, состояние не меняется.
3. **Условие:** у сессии A в БД `expires_at` в прошлом. **Действие:** запрос с этим токеном. **Ожидаемый результат:** 401.
4. **Условие:** после регистрации и входа A. **Действие:** посмотреть таблицы `persons` и `sessions`. **Ожидаемый результат:** в `password_hash` нет исходного пароля, в `sessions` нет значения, совпадающего с выданным токеном.
5. Для SR-10 — по критерию приёмки: 5 неверных паролей → верный пароль получает 429 и токен не выдаётся; после окончания блокировки вход проходит.

**Ограничения и последствия:**

- Украденный токен работает до выхода или 24 часов — это осознанный компромисс ради удобства.
- Блокировку SR-10 можно использовать, чтобы на 15 минут не пускать в чужой аккаунт (зная логин). Для нашего продукта это меньшее зло, чем подбор пароля.
- Новые обработчики обязаны брать пользователя через `userFrom(r)`; это правило для всей команды при код-ревью.

### D-02. Проверка владельца — в том же запросе к БД, что и действие

**Контекст:** T-01 — участник подставляет `id` чужой регистрации в `DELETE /registrations/{id}`; T-05 — пользователь запрашивает `GET /events/{id}/participants` чужого мероприятия. Идентификаторы у нас последовательные (`BIGSERIAL`) и легко перебираются, а `id` мероприятий видны в публичном списке. Связанные SR-04, SR-09.

**Решение:**

- Отмена регистрации — один SQL-запрос, в котором есть и действие, и условие владельца:
  `UPDATE registrations SET status = 'cancelled' ... WHERE id = $1 AND person_id = <пользователь из сессии> AND status = 'active'`.
- Список участников — сначала `SELECT ... FROM events WHERE id = $1 AND organizer_id = <пользователь из сессии>`, и только если строка нашлась, отдаём участников (только имя, контакты и время записи активных регистраций).
- Если строка не нашлась (чужой объект, несуществующий или уже отменённый), ответ всегда одинаковый — **404**, без различия «нет такого» и «нет прав».

Код: `handleCancelRegistration` в `internal/api/registration_handlers.go`, `handleParticipants` в `internal/api/event_handlers.go`.

**Обоснование:**

- Если сначала прочитать запись, проверить владельца в Go и потом отдельно обновить, то проверку легко забыть в новой ветке кода, а между проверкой и изменением есть промежуток. Условие внутри `WHERE` нельзя «обойти»: нет строки — нет изменения.
- Одинаковый 404 не даёт перебором `id` узнать, какие регистрации и мероприятия существуют.
- Мы не полагаемся на то, что `id` секретные. Случайные UUID усложнили бы перебор, но не заменяют проверку владельца, поэтому `id` оставили числовыми.

**Связанные угрозы:** T-01, T-05 (а также T-03 — условие `status = 'active'`, см. D-03)

**Связанные требования:** SR-04, SR-09

**Будущая проверка** (дополняет критерии SR-04 и SR-09):

1. **Условие:** у A активная регистрация R, на мероприятии N свободных мест. **Действие:** B отправляет `DELETE /registrations/R`, затем `DELETE /registrations/999999`. **Ожидаемый результат:** оба ответа 404 с одинаковым телом; R осталась `active`, свободных мест по-прежнему N.
2. **Условие:** то же. **Действие:** A отправляет `DELETE /registrations/R`. **Ожидаемый результат:** 204, R стала `cancelled`, мест N + 1.
3. **Условие:** мероприятие X организатора O1, на него записан участник P. **Действие:** `GET /events/X/participants` от организатора O2, от участника P и от O1. **Ожидаемый результат:** O2 и P получают 404 без данных; O1 получает список, где есть только активные участники, и в ответе нет логинов и хэшей.

**Ограничения и последствия:**

- Свою уже отменённую регистрацию пользователь тоже видит как «не найдена» (404). Для клиента это нормально, в `GET /registrations/my` статус виден.
- Если мы добавим функцию «организатор отменяет регистрацию участника», для неё нужен отдельный запрос с условием `organizer_id = <пользователь>` через join с мероприятием, а не ослабление текущего условия.

### D-03. Места и записи меняются одной атомарной операцией с условием

**Контекст:** T-02 — два участника одновременно записываются на последнее место; T-03 — повторная или параллельная отмена дважды возвращает место; T-04 — один участник шлёт много параллельных записей. Связанные SR-05 (не больше вместимости, в т.ч. при одновременных запросах), SR-06 (одна активная запись на человека).

**Как мы пришли к решению (контрпример к первоначальной цепочке).**

Исходное предположение на S03 было: «в транзакции проверяем, что `free_seats > 0`, потом создаём запись и уменьшаем счётчик — значит, переполнения не будет». Контрпример для нашего стека: в PostgreSQL по умолчанию уровень изоляции READ COMMITTED, и обычный `SELECT` ничего не блокирует. Две транзакции одновременно читают `free_seats = 1`, обе проходят проверку и обе делают `INSERT`. Если счётчик обновляется как `SET free_seats = <прочитанное значение> - 1`, обе запишут `0` — в итоге **две активные записи на одно место при счётчике 0**, и даже ограничение `CHECK (free_seats >= 0)` ничего не заметит. Ошибка «тихая».

Что это изменило в цепочке:

- **D:** слово «транзакция» само по себе не гарантия. Гарантию даёт условное изменение строки мероприятия, которое PostgreSQL выполняет с блокировкой строки (см. решение ниже).
- **SR-05:** критерий приёмки уже требует проверки одновременными запросами; при разборе мы дополнительно заметили обратный путь — отмену. Повторная отмена тоже меняет счётчик, поэтому в критерий SR-05 добавили «повторная отмена не увеличивает число мест», а в модель — T-03.
- **Будущая проверка:** должна быть именно **конкурентной**. Последовательный тест (сначала один запрос, потом второй) проходит и для неправильной реализации, поэтому он ничего не доказывает.

**Решение.** Запись на мероприятие (`POST /events/{id}/registrations`) — одна транзакция:

1. `UPDATE events SET free_seats = free_seats - 1 WHERE id = $1 AND status = 'published' AND free_seats > 0`. Если обновлено 0 строк — отказ (409 «мест нет» или 404), ничего не изменилось.
2. `INSERT INTO registrations (..., status) VALUES (..., 'active')`. В БД есть частичный уникальный индекс `UNIQUE (event_id, person_id) WHERE status = 'active'`. Если у человека уже есть активная запись, `INSERT` падает, транзакция откатывается и место возвращается (409).

Отмена (`DELETE /registrations/{id}`) — одна транзакция: условный `UPDATE` регистрации из D-02 (`... AND status = 'active'`), и **только если он изменил строку** — `free_seats = free_seats + 1`.

Последняя линия защиты в схеме: `CHECK (free_seats >= 0 AND free_seats <= capacity)`.

Код: `handleRegisterForEvent` и `handleCancelRegistration` в `internal/api/registration_handlers.go`, ограничения в `internal/storage/migrations/001_init.sql`.

**Обоснование.** `UPDATE` с условием в PostgreSQL блокирует строку мероприятия. Второй одновременный запрос ждёт, пока первая транзакция завершится, и затем заново проверяет `free_seats > 0` уже на новой версии строки. Поэтому ситуации «оба увидели одно свободное место» не бывает. Решение «проверить и изменить» происходит в одной операции БД, а не в коде Go по прочитанному раньше значению. Уникальный индекс закрывает T-04 даже при параллельных запросах одного человека, а условие `status = 'active'` при отмене — T-03.

Другие варианты, которые обсуждали: `SELECT ... FOR UPDATE` даёт ту же гарантию, но больше кода и легко забыть `FOR UPDATE`; уровень SERIALIZABLE тоже корректен, но требует повторять транзакцию при ошибке сериализации; считать места через `COUNT(*)` активных записей без счётчика не спасает от гонки без блокировки.

**Связанные угрозы:** T-02, T-03, T-04

**Связанные требования:** SR-05, SR-06

**Будущая проверка** (дополняет критерии SR-05 и SR-06; запросы отправлять **параллельно**, например из 20 потоков):

1. **Условие:** мероприятие с вместимостью 1, 20 разных участников вошли. **Действие:** все 20 одновременно отправляют запрос записи. **Ожидаемый результат:** ровно один 201, остальные 409; в БД одна активная запись, `free_seats = 0`.
2. **Условие:** мероприятие с вместимостью 5, участник A вошёл. **Действие:** A одновременно отправляет 10 запросов записи. **Ожидаемый результат:** один 201, остальные 409; у A одна активная запись, `free_seats = 4`.
3. **Условие:** у A активная запись на мероприятие с `free_seats = 4`. **Действие:** A одновременно отправляет 5 запросов отмены этой записи. **Ожидаемый результат:** один 204, остальные 404; `free_seats = 5`, не больше.
4. **Условие:** любое мероприятие. **Действие:** напрямую в БД выполнить `UPDATE events SET free_seats = -1`. **Ожидаемый результат:** ошибка нарушения ограничения `free_seats_range`.

**Ограничения и последствия:**

- Все записи на одно мероприятие выполняются по очереди (из-за блокировки строки). Для нашего масштаба это незаметно; при очень популярных мероприятиях это узкое место.
- `free_seats` — хранимый счётчик. **Любой** новый код, который меняет регистрации (отмена мероприятия, отмена организатором), должен менять счётчик в той же транзакции и с тем же условием по статусу, иначе он разъедется с реальными записями.
- Решение рассчитано на PostgreSQL (поведение блокировок при READ COMMITTED); при смене СУБД его надо перепроверить.

## Остальные угрозы

Угрозы не из приоритетного набора закрыты локальными мерами в коде, без отдельного D:

- **T-07** — `POST /events` проверяет роль из сессии (D-01) и отвечает 403 участнику (SR-07).
- **T-09** — в `PATCH /me` можно передать только `name` и `contacts`; JSON с неизвестными полями (например, `role`) отклоняется целиком (SR-08).
- **T-10** — публичные ответы собираются из отдельных структур (`eventResponse`), где из данных организатора есть только имя; хэш пароля не попадает ни в один ответ (SR-02, SR-11).
